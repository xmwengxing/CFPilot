# CFPilot 0.9.6

这轮只做**优选速度**：把「测出来永远 0.1~0.5 MB/s」的三个根因修掉，并用真机数据把「为什么别人家显示 20-50 MB/s」讲清楚。

## 修复

### 采样种子写死，每次都测同一批 IP

`--seed` 默认值曾经是固定的 `24301`，而采样是确定性的（mulberry32）：
**只要 `--sample` 不变，每次运行得到的候选 IP 列表 100% 一模一样**。
如果那批 IP 恰好落在本地运营商的劣质路由段上，重跑一百次、换多少个时间段，
测出来的永远是同一批慢 IP —— 用户只会得出「优选坏了」的结论。

现在默认每次随机（`randomSeed()` = 时间 ^ 随机数），**每次探索不同的 IP 子集**；
显式 `--seed` 仍然固定、可复现（排查与对比时用）。

### 测速连接数从 3 提到 8（本次提升最大的一项）

真机直连实测**同一个 IP、同一时段**，吞吐随连接数近似线性增长：

| 连接数 | 吞吐 |
|---|---|
| 1 | 0.12 MB/s |
| 3 | 0.47 MB/s |
| **8** | **1.15 MB/s** |
| 16 | 2.22 MB/s |

跨境链路的瓶颈是**单连接的丢包 / 拥塞窗口**，不是带宽上限 ——
用 1~3 条会系统性低估 2~4 倍。CLI 与桌面版同步改为默认 8 条（`--speed-conns` 可调），
更贴近浏览器/客户端的真实多连接行为。

同 seed、同一时段 A/B 实测（300 候选、测前 10）：

| | 下行范围 | 中位 |
|---|---|---|
| 改前（3 条） | 0.2 ~ 0.5 MB/s | 0.4 |
| 改后（8 条） | 1.1 ~ 1.9 MB/s | **1.4** |

顺带：进度日志现在会带上机房（`测速 3/10 [LAX] 1.4 MB/s`）。

### 探针端点：测速块改为模块级常量

`/__edge_probe` 原先每个请求都 `new Uint8Array(64KB)` 再跑 65536 次循环填充；
一条候选开 8~16 条连接时纯属白烧 CPU。改为模块级共享缓冲（永不修改）。

## 优化：网段权重按真机复测更新

用户怀疑「之前屏蔽的网段是网络不稳定导致的误判」—— 复测结论：**部分成立**。

| 网段 | 旧表 | 复测 | 结论 |
|---|---|---|---|
| `104.24.0.0/14` | 7/12 | **11/12** | 最好的一段 |
| `188.114.96.0/20` | 3/12 | **9/12** | **被误杀 3 倍** → 权重 0.3→0.75 |
| `172.64.0.0/13` | 1/12 | **5/12** | **被误杀 5 倍** → 权重 0.1→0.4 |
| `162.158.0.0/15` | 2/12 | 4/12 | 权重 0.2→0.3 |
| `141.101.64.0/18` | 2/12 | 0/12 | 高估 → 权重 0.2→0.05（保留探针）|
| `103.22.200.0/22` / `197.234.240.0/22` / `198.41.128.0/17` / `131.0.72.0/22` | 0/12 | 0/12 | **TCP 层就不通**，不是测错 |
| `108.162.192.0/18` | 0/12 | 0/12 | TCP 3/3 能连，但 TLS/HTTP 不应答 |

也就是说：**大部分「0 可用」是真的**（路由层不可达），
但有两段确实被低估、已按复测加权。另外留一点权重给「0/12」的网段后，
本次扫描真的从 `141.101.64.0/18` 里选出了可用 IP（1.8 MB/s）。

## 关于「别人家显示 20-50 MB/s」

参考项目 CFData-WEB 的测速实现（已读其源码 `tasks_speed.go`）：
**单连接、6 秒窗口、目标 `speed.cloudflare.com/__down`、TTFB 之后开始计时**。
用同一方法在本机同一时段实测：**0.12~0.18 MB/s**（16 条并行才 3.0 MB/s）。

所以差异不在测速算法，而在：

1. **时段**：这是电信晚高峰（23:00），到 CF 的跨境链路丢包严重。
   同一台机器在早上/凌晨跑单连接可以达到几十 MB/s —— 那两个工具的 20-50 MB/s 多半是那个时段跑出来的；
2. **测量对象不同**：它们测的是「到 `speed.cloudflare.com` 这个通用目标」的带宽，
   我们测的是「到**你自己的数据面域名**」的带宽 —— 后者才决定节点能不能用。
   这正是它们选出的 IP 导入客户端后全是 **-1** 的原因（能用 ≠ 对你的站点可用）；
3. **并发口径**：我们把 8 条连接的聚合带宽作为「下行」，它们只算 1 条。

**建议的公平对比方式**：在同一 10 分钟窗口内，先跑本项目、再跑参考项目，
否则时段差异（3~10 倍）会完全盖过工具差异。

## 验证

- 单元测试 **540 passed**（+7：种子随机性 + 权重表回归）。Go `test`/`vet`/`gofmt` 全绿。
- 真机：A/B 同 seed 对比 0.4 → 1.4 MB/s（中位）；最终构建再跑一次得 1.0~1.8 MB/s。
- 探针端点 `Content-Length` 的结论：本地 workerd 实测对流式响应会被运行时丢弃
  （仍发 `Transfer-Encoding: chunked`），所以「加长度让客户端收满即止」在 Workers 上走不通，
  客户端改为按固定时长窗口结算（现有实现已是如此），代码里已写明，避免以后重复踩。

## 升级提示

内核与 CLI 都有改动，需要重新部署 + 更新工具：

```bash
npx -y cfpilot@latest scan --host <数据面域名>   # 新 CLI（默认 8 连接、每次换样本）
npx -y cfpilot@latest deploy                     # 重新部署内核
```
